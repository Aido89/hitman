# Hitman IT — сайт на Django

Полный рерайт статического сайта и более позднего React-варианта (см. `../Portfolio redesign/`) на Django с шаблонами и ванильным JS. Чёрно-красная тема, тот же контент и та же бизнес-логика (калькулятор сметы, курс Google Workspace), но:

- реально запускается и проверяется в этой среде (Node.js здесь недоступен, Python — доступен);
- админка — не самописный React-компонент, а встроенная `django.contrib.admin`.

## Запуск

```bash
cd django_site
pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser   # для входа в /admin/
python manage.py runserver
```

Открыть `http://127.0.0.1:8000/`.

## Структура

- `config/` — настройки, корневой `urls.py`.
- `pages/` — статические разделы: главная, «Обо мне», Направления/Навыки/Кейсы/Форматы, блог. Контент — в `pages/data.py` (без БД, как в оригинале — это авторский контент, не то, что должно редактироваться через админку прямо сейчас).
- `orders/` — конструктор сметы. `models.OrderLead` — то, что видно в `/admin/`. `static/js/order_constructor.js` — калькулятор цен (1:1 с логикой из React/оригинала), считает всё на клиенте; при клике «Оформить в WhatsApp» лид дополнительно сохраняется через `POST /smeta/submit/`.
- `training/` — курс Google Workspace. `training/data.py` — 31 модуль (RU/KZ). `static/js/training.js` — рендер модулей, квизы, прогресс (SVG-кольцо, без Chart.js).
- `templates/` — все HTML-шаблоны, наследуются от `templates/base.html`.
- `static/css/site.css` — вся стилистика (чёрно-красная палитра, Playfair Display, карточки, конструктор).

## Админка

`/admin/` — стандартная Django-админка.

- `OrderLead` (`orders/admin.py`): список заявок, фильтр по статусу/типу услуги, инлайн-редактирование статуса, поиск.
- `HeroSlide` (`pages/models.py`): слайды баннера на главной. Добавление/удаление/реордер (`order`)/вкл-выкл (`is_active`) — прямо из списка в админке, фото — обычная загрузка файла. Шаблон (`templates/pages/home.html`) рендерит их циклом, ничего хардкодить не нужно.
- `GalleryPhoto` (`pages/models.py`): фото для `/gallery/`, добавленные через админку (категория + файл + подпись). Дополняют, не заменяют, фото, разложенные вручную по папкам `static/img/gallery/<категория>/` (`pages/gallery.py` сливает оба источника) — старый способ («кинуть файл в папку и задеплоить») по-прежнему работает.
- `HomeSection` (`pages/models.py`): 4 карточки-направления на главной («Услуги и цены», «Кейсы»...) — заголовок, описание, иконка (из готового набора), ссылка. Правится и переставляется прямо в списке.
- `ServiceCard` (`pages/models.py`): все карточки `/services/` — заголовок, «для кого», цена, описание, состав работ (`groups`, JSON-поле: `[["Группа", ["тег1", "тег2"]], ...]`). `image`/`icon` — не загрузка, а путь к уже существующему файлу в `static/` (текст, не файл) — для новой картинки её всё ещё нужно сначала положить в `static/img/...` и задеплоить.
- `Testimonial`, `Metric` (`pages/models.py`): отзывы на главной и цифры «В цифрах» на `/services/` — текст + порядок, ничего сложного.
- `Case` (`pages/models.py`): кейсы на `/cases/` — задача/что сделано/результат + `metrics` и `tags` (JSON-поля, тот же формат `[["значение", "подпись"], ...]` / `["тег", ...]`).
- `RepairWarranty`, `RepairPriceGroup` (`pages/models.py`): плашка гарантии и таблица цен на ремонт на `/services/`. `RepairWarranty` — единственная строка (текст плашки), `RepairPriceGroup.items` — JSON-список `[["Название работы", "цена"], ...]`.
- `BlogPost` (`pages/models.py`): статьи `/blog/` — `body` (JSON-поле) хранит список блоков `[["h2", "Заголовок"], ["p", "Текст"], ["quote", "Цитата"], ...]`, ровно то, что раньше было в `data.py`.
- `CourseModule` (`training/models.py`): 31 модуль курса Google Workspace. `content_ru`/`content_kk` — JSON-поля с полной вложенной структурой модуля (`goal`/`interactive`/`case`/`assignment`/`practice`/`quiz`) на каждом языке — редактирование через сырой JSON в админке, не через отдельные поля формы (сложность/объём контента не оправдывали 10+ полей × 2 языка × 31 модуль). `module_id` — не PK Django, а явное поле 0–30, на которое ссылается `training/data.py` (`MATERIALS_MODULE_IDS`, иконки) — реордер в админке не собьёт эти ссылки.

Все перечисленные модели раньше жили в `pages/data.py`/`training/data.py` — миграции-сиды (`pages/migrations/0004_...`, `0006_...`, `training/migrations/0002_...`) перенесли текущий контент в БД один раз, дальше он живёт только в БД. Модули курса — единственное исключение: `training/data.py` `MODULES` намеренно оставлен (470 строк, 31 модуль × 2 языка — вручную переносить рискованно), миграция-сид импортирует его напрямую; сам список больше ничем не используется — правки только через `/admin/`.

Загруженные через админку файлы лежат в `MEDIA_ROOT` (`media/`, не в git). **Известное ограничение:** прод крутит 2 реплики без общего volume (`k8s/deployment.yaml`) — загрузка попадёт на диск только того пода, который принял запрос, и не переживёт рестарт/передеплой. Для реальной надёжности в проде нужен shared volume (ReadWriteMany) под `MEDIA_ROOT` либо `django-storages` + S3/MinIO.

## Проверено вручную (в этой сессии)

- Все страницы отдают 200.
- Конструктор: пересчёт суммы при выборе тайлов/опций, переход по шагам, генерация ссылки WhatsApp, сохранение заявки в БД — всё проверено через реальные клики/JS-вызовы в браузере.
- Курс: рендер 31 модуля, переключение, проверка квиза (правильный/неправильный ответ), обновление прогресса — проверено.
- Админка: вход, список заявок, фильтры — проверено.

## Что ещё не сделано

- Реальное фото в hero (используется эмодзи/иконки вместо фото).
- Production-настройки (DEBUG=False, ALLOWED_HOSTS, статика через whitenoise/nginx, секреты через переменные окружения — секретный ключ и DEBUG уже читаются из env, но дефолты не для прод).
